# Gleave 방향성 점검 12 — 프로젝트 기억 이력 재적용 UI

기준: 2026-10-28, `feat/unified-chat`

## 목표

사용자가 기존 프로젝트 기억을 실수로 바꿨거나 이전 결정으로 돌아가야 할 때, **이전 버전의 내용을 명시적으로 선택하여 다시 적용**할 수 있게 한다. 과거 변경을 삭제하거나 출처를 거짓으로 바꾸지 않는다.

## 변경 사항

- 기존 `MemoryDetail.tsx` 변경 이력의 각 버전에 `vN 내용 다시 적용` 선택지를 추가한다.
- 현재 활성 기억과 내용이 다른 역사적 버전 중 `new_content`가 존재하는 버전만 제안한다.
- 사용자 확인창에 현재 내용, 재적용할 이전 내용, 기존 출처 연결 유지, 이력 보존을 명시한다.
- 새 쓰기 API를 만들지 않고 기존 `PUT /v1/projects/{project_id}/memories/{memory_id}`에 이전 내용과 **현재 expectedVersion**을 전달한다.
- 서버가 소유권, 프로젝트 권한, 활성 상태, 최신 버전을 다시 검사하고 SQLite 트랜잭션으로 새 `updated` revision을 기록한다. 기존 이력은 유지된다.
- 철회된 기억의 재활성화는 제공하지 않는다. 과거 원본 메시지 연결 자체를 되돌리는 기능도 아니다.

## 검증 기준

- 이전 내용으로 재적용한 후 버전은 증가해야 하고, 전후 내용·기존 원본 출처·활성 프로젝트 컨텍스트는 일치해야 한다.
- 낡은 expectedVersion 요청은 실패해야 하며, 철회된 기억은 업데이트할 수 없어야 한다.
- React/TypeScript 빌드, 관련 Python 회귀 테스트 및 Ruff를 실행해 기록한다.
- 실제 Windows 패키징 GUI를 통한 클릭·스크린리더 수동 E2E는 별도 확인이 필요하다.

## 유의 사항 / 후속 작업

- 기록 자체를 과거로 되감는 기능이 아니라, 이전 **텍스트를 새 수정으로 추가**하는 방식이다.
- 과거의 `source_message_id`나 다른 프로젝트에서 승인된 기억을 가져오지 않는다.
- 팀 권한은 여전히 로컬 헤더 기반이며 실제 원격 신원 인증이 아니다.
- 삭제된/철회된 기억을 재활성화하거나 변경 이력의 영구 삭제·보존 기간·법적 삭제 요청을 해결하는 정책은 별도로 설계해야 한다.
